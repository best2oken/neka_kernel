# NEKA — New EKA. Bare-metal x86 kernel, планировщик в духе EKA2

Минимальное ядро (multiboot, i386/x86_64, protected/long mode), демонстрирующее ключевую
идею планировщика Symbian EKA2 — битовую карту приоритетов и мгновенный выбор
следующего потока вместо перебора очередей.

## Параллели с настоящим EKA2 (kernel/eka/nkern/x86/ncsched.cia)

| EKA2 (реальный, asm)                          | ToyKernel (упрощённый, C)                |
|-----------------------------------------------|-------------------------------------------|
| `bsr ecx, eax` — найти старший бит             | `find_highest_bit()` в sched.c            |
| `iQueue[p]` — кольцевая очередь на приоритет   | `ready_queue[priority]` + `next` (кольцо) |
| `iRescheduleNeededFlag`                        | не реализовано (кооперативный режим)      |
| `mov [esi+iSavedSP], esp` / `mov esp, [...]`  | `context_switch.s` — тот же принцип       |
| `iKernCSLocked` (big kernel lock)              | не реализовано (однопоточный кооп. режим) |
| SMP (`nkernsmp`)                               | не реализовано (однопроцессорный демо)    |

## Пересборка и запуск локально

Требуется: gcc (с поддержкой -m32 и multilib), nasm, GNU ld, qemu-system-i386.

```bash
# Ubuntu/Debian:
sudo apt install gcc-multilib nasm qemu-system-x86 grub-pc-bin xorriso

cd toykernel
chmod +x build.sh
./build.sh

# Запуск headless (вывод через serial):
qemu-system-i386 -kernel build/toykernel.bin -display none -serial stdio

# Запуск с графическим окном (увидишь VGA-текст напрямую):
qemu-system-i386 -kernel build/toykernel.bin
```

## Структура

- `boot/boot.s` — multiboot-заголовок + переход в C
- `kernel/sched.c` — планировщик (bitmap приоритетов, round-robin в кольце)
- `kernel/context_switch.s` — реальный ассемблерный свитч стека
- `kernel/terminal.c` — вывод в VGA text mode + serial (COM1)
- `kernel/timer.c` — PIC remap + программирование PIT (таймер пока не подключён к прерыванию — планировщик кооперативный, потоки сами зовут `sched_yield()`)
- `kernel/main.c` — создание демо-потоков и главный цикл

## Известное ограничение (сделано намеренно, для простоты)

Планировщик **кооперативный**: потоки должны сами вызывать `sched_yield()`.
В настоящем EKA2 таймер по IRQ0 (`TimesliceTick`) сам прерывает поток —
для этого нужен IDT + ISR-обработчик прерываний, которого пока нет.

## 64-битная версия (long mode) — build64.sh

Второй, независимый вариант: демонстрация перехода из 32-битного protected
mode (куда GRUB ставит нас по multiboot-спеке) в настоящий 64-битный long
mode — тот самый шаг, без которого нативная загрузка на современном
железе (Alder Lake и т.п.) невозможна.

### Пересборка и запуск локально

```bash
sudo apt install gcc nasm qemu-system-x86 grub-pc-bin xorriso

cd toykernel
chmod +x build64.sh
./build64.sh

# ВАЖНО: qemu -kernel не грузит ELF64 напрямую (multiboot-загрузчик QEMU
# требует 32-битный ELF), поэтому нужен настоящий GRUB через ISO:
mkdir -p isodir/boot/grub
cp build/toykernel64.bin isodir/boot/
cat > isodir/boot/grub/grub.cfg << 'EOF'
set timeout=0
menuentry "ToyKernel64" {
    multiboot /boot/toykernel64.bin
    boot
}
EOF
grub-mkrescue -o build/toykernel64.iso isodir

qemu-system-x86_64 -cdrom build/toykernel64.iso -serial stdio
```

Готовый `toykernel64.iso` уже собран и лежит рядом — можно сразу
`qemu-system-x86_64 -cdrom toykernel64.iso -serial stdio` без пересборки.

### Что происходит в boot64.s

1. Multiboot header → GRUB грузит нас в 32-бит protected mode
2. Строим page tables (PML4→PDPT→PD), identity map первого 1 ГБ (2MB-страницы)
3. `CR4.PAE = 1` — включаем Physical Address Extension
4. `CR3 = адрес PML4`
5. `EFER.LME = 1` через MSR 0xC0000080 — разрешаем long mode
6. `CR0.PG = 1` — включаем paging → CPU входит в IA-32e compatibility submode
7. **Far jump** на 64-битный code segment (GDT-дескриптор с L-битом) — точка входа в настоящий long mode
8. 64-битный стаб настраивает сегменты/стек и зовёт `kernel_main64()` (обычный C, System V AMD64 ABI)

### Пойманный по пути баг (типичный для bare-metal)

GCC на `-O2` автовекторизировал цикл очистки VGA-буфера через SSE
(`movdqa`/`movaps`), а FPU/SSE state после входа в long mode ещё не
инициализирован (`CR0.EM`/`CR4.OSFXSR`) — это давало `#UD` (invalid
opcode) → мгновенный triple fault (IDT тоже пуст, обрабатывать
исключение нечем). Фикс: `-mgeneral-regs-only` при компиляции
kernel-кода, пока не настроен FPU.

### Следующие шаги для этой ветки

1. ~~Настоящий IDT + обработчики исключений~~ ✅ **готово**
2. ~~Инициализация FPU/SSE~~ ✅ **готово** — `kernel/fpu.c`, `-mgeneral-regs-only` больше не нужен
3. ~~Порт планировщика на 64-битную ABI~~ ✅ **готово** — `kernel/sched64.c` + `kernel/context_switch64.s`, НАСТОЯЩИЙ preemptive multitasking (таймер вытесняет потоки сам через IRQ0, ни одного `sched_yield()` в коде потоков)
4. ~~Kernel panic вместо непроверенных ошибок инициализации~~ ✅ **готово**
5. ~~Виртуальная память per-process (CR3 switch)~~ ✅ **готово**
6. ~~User mode (ring3) + syscalls~~ ✅ **готово**
7. ~~Динамический heap (kmalloc/kfree)~~ ✅ **готово**
8. ~~Драйвер клавиатуры (IRQ1)~~ ✅ **готово**
9. ~~UEFI-загрузка~~ ✅ **готово**
10. ~~APIC вместо legacy PIC8259~~ ✅ **готово** — `kernel/apic.c`. Local APIC включён через MSR (`IA32_APIC_BASE`), таймер откалиброван через PIT channel 2 busy-wait (без единого прерывания — классическая техника для калибровки ДО того как IDT/IOAPIC вообще настроены), IOAPIC роутит клавиатуру (ISA IRQ1 → вектор 33), legacy PIC полностью замаскирован. Реальные адреса LAPIC/IOAPIC читаются из ACPI MADT (`apic_apply_acpi_bases()`), а не хардкожены.
11. ~~`NKern::Lock()/Unlock()`~~ ✅ **готово** — `kernel/nkern_lock.c`. Настоящий cross-CPU spinlock (`big_kernel_lock`) + per-CPU счётчик вложенности (`preempt_disable_count`) + `cli`/`sti` с сохранением исходного `IF` (паттерн `spin_lock_irqsave` из Linux). `kmalloc()`/`kfree()` обёрнуты в лок.
12. ~~SMP~~ ✅ **готово на GRUB-пути** (30 секунд, 500+ итераций, 0 exceptions) — `kernel/acpi.c`, `kernel/smp.c`, `kernel/ap_trampoline.s`. Настоящий второй процессор поднят через ACPI MADT + INIT-SIPI-SIPI, выполняет реальный код ядра параллельно с BSP. **UEFI-путь всё ещё падает** после нескольких успешных итераций — см. неразрешённую проблему в конце этого раздела.
13. Драйвер клавиатуры не работает на AP (IOAPIC redirect только на BSP) — не проблема для текущей демонстрации
14. Per-CPU run queues вместо одной общей — см. известное ограничение ниже

### Как устроен SMP (acpi.c, smp.c, ap_trampoline.s)

**ACPI-обнаружение CPU** (`acpi.c`): полный парсинг RSDP→RSDT/XSDT→MADT — на UEFI RSDP берётся напрямую из `EFI Configuration Table` (`LibGetSystemConfigurationTable`), на BIOS/GRUB — честное сканирование памяти (EBDA + диапазон `0xE0000-0xFFFFF`), как требует ACPI spec для платформ без UEFI-сервиса. Из MADT достаются: список включённых Local APIC ID (реальная топология CPU, не константа), и реальные физические адреса LAPIC/IOAPIC (Type 0 и Type 1 entries).

**AP trampoline** (`ap_trampoline.s`): Application Processor стартует в 16-битном real mode по физическому адресу `vector<<12`. Файл собирается отдельно как raw binary (`-f bin`, без ELF) и копируется BSP на фиксированный адрес `0x8000` перед отправкой `INIT-SIPI-SIPI` (адрес проверяется на безопасность через `memmap_region_is_safe()` перед записью — под UEFI нельзя полагаться на BIOS-эра конвенции "низкая память свободна"). Проводит AP через real mode → 32-бит protected → 64-бит long mode, используя уже готовый `kernel_pml4` и настоящую GDT ядра. "Почтовый ящик" на фиксированном смещении `0x100` от начала блоба передаёт: физ.адрес page tables, адрес структуры GDT, стек и entry point для AP — raw binary не хранит символов, поэтому смещения синхронизированы вручную между asm и C.

**Восемь реальных багов, найденных через тестирование:**
1. **Двойная косвенность в `lgdt`** — почтовый ящик хранил *адрес* структуры `gdt_ptr_t`, а `lgdt [mbox_real_gdt_ptr]` читал 10 байт прямо из ящика вместо использования этого адреса.
2. **FPU/SSE — per-core состояние.** `fpu_init()` на BSP не действует на AP — первая же SSE-инструкция на AP дала `#UD`/`#GP`.
3. **IDTR — тоже per-core.** AP успевал выполнить один тик потока, но при первом же срабатывании *своего* LAPIC-таймера мгновенно triple fault'ился.
4. **Невыровненный стек AP.** `kmalloc()` не гарантирует 16-байтовое выравнивание — вершина стека AP оказалась не выровнена для `movaps`.
5. **Per-CPU состояние в глобальных переменных** — `loaded_cr3` и `sched64.current` были общими на все ядра, хотя CR3 и "текущий поток" — состояние конкретного процессора. Оба стали per-CPU массивами.
6. **`context_switch64` не сохранял `RFLAGS`** — было безопасно, пока переключения происходили строго из прерывания. Демо `NKern_Lock`/`Unlock` вызывает `sched64_reschedule()` прямо из кода потока — новый путь, ломающий это допущение. Фикс: `pushfq`/`popfq` в `context_switch64.s`, плюс `cli`/`sti` с сохранением `IF` в `NKern_Lock`/`Unlock`.
7. **`build_uefi.sh` молча не компилировал `acpi.c`/`smp.c`** — `ld -shared` не ругается на неразрешённые символы, сборка "успешно" завершалась, но упала бы в runtime. Пойман через `nm -u`, добавлена автоматическая проверка прямо в скрипт.
8. **Общий (per-CPU) TSS отсутствовал у AP** — сознательно пропустили `ltr` для AP, посчитав, что ring3-код туда не попадёт. Расчёт был неверным: scheduler не привязывает потоки к ядрам, ring3 launcher мигрировал на AP и получил `#GP`/`#DF` на первом же `int 0x80` (`TSS.RSP0` не существовал на этом ядре — CR2 в дампе был `0xFFFFFFFFFFFFFFF8`, ровно "(0-8)"). Фикс: `gdt_setup_cpu_tss(cpu_idx)` — свой TSS и свой kstack на каждое ядро.

**Девятый баг, найденный при доразборе — архитектурный, требовал пересмотра логики блокировки планировщика:** `sched64_reschedule()` отпускала лок и включала прерывания **до** фактического `context_switch64()`. Это делало `prev->state=READY` видимым для другого ядра ДО того, как `prev->rsp` реально сохранён — другое ядро могло попытаться запустить `prev` по устаревшему стеку. Фикс: отдельная пара `NKern_LockForSwitch()`/`NKern_UnlockAfterSwitch()` — разблокировка происходит только после того, как переключение реально случилось (из `thread_start64` для новых потоков, или сразу после возврата из `context_switch64()` для возобновляемых).

**Десятый баг, найденный попутно:** `kprint()` не был защищён никаким локом — два ядра, печатающие одновременно, давали посимвольно перемешанный вывод (наблюдалось буквально: `"[B cpu...] tick [smp] AP confirmed alive.\n0x...1 AS=OK"` — две разные строки склеились). Добавлен отдельный `print_lock` с `cli`/`sti` (не переиспользуя `NKern_Lock`, чтобы не тащить его reschedule-семантику в консольный вывод). Заодно поймали и исправили соседний баг — `term_row` рос без ограничения, уходя за пределы настоящего VGA-буфера (80×25); теперь оборачивается.

**Известное ограничение (не решено):** планировщик использует **один общий указатель** `ready_queue[prio]` для round-robin на все ядра — если одно ядро чаще "выигрывает" вращение кольца, другое может систематически видеть `next==prev` и переставать получать новые потоки (не краш, просто неравномерная нагрузка). Настоящее решение — per-CPU run queues с периодическим load balancer'ом.

**Неразрешённая проблема (после всех вышеперечисленных фиксов) — расширенный отчёт после второго раунда диагностики:**

На UEFI-пути при `-smp 2` воспроизводится крах, но **не всегда одинаковый** — три разных симптома в разных прогонах:
- `#UD` по адресу `RIP=0x80201A` (детерминированно повторяется чаще всего)
- `#PF` (instruction fetch, not present) по адресу `RIP=0x1001E8480` — младшие 32 бита этого адреса (`0x1E8480`) равны **2 000 000 в десятичной** — ровно то число итераций, которое используют busy-loop в потоках A/B. Похоже на порчу стека, где значение локальной переменной цикла оказалось там, где ожидался адрес возврата.
- `#UD` по адресу `RIP=0xB0001` — это внутри классической "VGA memory hole" (`0xA0000-0xBFFFF`), физически не предназначенной для исполнения кода.

Все три адреса — дикие переходы за пределы реального runtime-адреса загрузки ядра (проверено вычитанием линк-time смещения `kernel_main64` от напечатанного runtime-адреса).

**Проверены и исключены как причина именно ЭТОГО краха** (каждый пункт — реальный самостоятельный баг, исправленный по ходу, но ни один не устранил этот конкретный краш):
- безопасность физического адреса trampoline (`0x8000`) — подтверждена через `memmap_region_is_safe()`, попадает в реально обнаруженный `EfiConventionalMemory`
- содержимое почтового ящика trampoline (`mbox[0..3]`) — все значения проверены диагностическим выводом, в разумных пределах, не испорчены
- per-CPU TSS для AP — исправлен, подтверждён рабочим на длинных прогонах
- порядок блокировки в `sched64_reschedule()` — исправлен, подтверждён на GRUB
- гонка в `kprint()` — исправлена, подтверждена (больше нет перемешанного посимвольно вывода)
- конкурентные вызовы `alloc_frame()`/`kmalloc()` между BSP и AP — проверено: в текущем коде ВСЕ такие вызовы происходят последовательно на BSP до старта AP, гонки здесь физически нет

**Урок, который стоит явно зафиксировать:** при попытке добавить `NKern_Lock()` вокруг `alloc_frame()` "для порядка" (защита от гипотетической будущей гонки) — ядро перестало грузиться вообще, даже на одном CPU! Причина: `alloc_frame()` вызывается из `paging_init_kernel_map()` **до** того как LAPIC замаплен и включён, а `NKern_Lock()` теперь (после фикса per-CPU state) внутренне читает LAPIC MMIO через `get_cpu_index()`. Получилась circular dependency: лок для защиты page-table аллокатора сам зависит от подсистемы, которую этот аллокатор же и подготавливает. Откачено — в текущем коде эта защита не нужна (гонки нет), но это ценный урок: **добавлять блокировку "на всякий случай" без проверки реальной цепочки инициализации — само по себе источник регрессий.**

**Диагностическая инфраструктура, оставленная в коде для продолжения расследования:**
- `main64.c`: печать реального runtime-адреса `kernel_main64` (нужно для UEFI, где адрес загрузки не `0x100000`, а выбирается прошивкой)
- `gdt64.c`: `gdt_get_tss_rsp0(cpu_idx)` — диагностика значения TSS.RSP0 по ядру
- `smp.c`: полный дамп значений почтового ящика (`mbox[diag]`) перед отправкой SIPI
- `idt.c`: дамп 24 qword памяти вокруг места краха при необработанном исключении
- Рабочий workflow подключения `gdb` к запущенному QEMU через `-s` (gdbstub на порту 1234) — можно ловить состояние ядра в момент зависания в `hlt`-цикле после краха (не сам момент краха — для этого нужен breakpoint/watchpoint, установленный ЗАРАНЕЕ по вычисленному runtime-адресу)

**Рабочая гипотеза для продолжения:** три РАЗНЫХ конкретных адреса в разных прогонах указывают на гонку, чувствительную к точному таймингу (а не детерминированный логический баг) — скорее всего где-то ещё остаётся операция с разделяемым состоянием между BSP/AP без должной синхронизации, которая не проявляется на GRUB-пути (возможно из-за иного тайминга/меньшей загрузки CPU без `-fpic`-специфичных накладных расходов) чаще, чем на UEFI. Кандидат, подозреваемый по совпадению `0x1E8480`=2000000: что-то в стеке потоков A/B, где живёт `volatile int i` busy-loop счётчик — возможно, связано с тем, что context switch происходит ПОСЕРЕДИНЕ этого цикла (что штатно и должно быть safe), но с чем-то ещё, что не учтено. Следующий шаг — hardware watchpoint на конкретный адрес стека потока A во время его busy-loop, через `gdb` `watch`, с заранее вычисленным runtime-адресом.

### Как устроен APIC (apic.c)

**Detection**: `CPUID.01h:EDX[9]` — если бит не установлен, `neka_panic()` (на любом x86_64 CPU обязан быть, отсутствие означает проблему с виртуализацией, а не "старое железо").

**MMIO-маппинг**: LAPIC (`0xFEE00000`) и IOAPIC (`0xFEC00000`) лежат в третьем GB адресного пространства — вне нашего обычного identity map первого 1GB. `paging_map_mmio_2mb()` (в `paging64.c`) добавляет отдельный `PDPT[3]` с флагом `PCD` (cache-disable — обязателен для MMIO, иначе CPU может закэшировать чтение регистра и никогда не увидеть его обновление через шину).

**Калибровка LAPIC-таймера**: частота LAPIC-таймера нигде не объявлена явно (зависит от шины/ядра), поэтому измеряется на месте — PIT channel 2 программируется на известную задержку (10ms), одновременно LAPIC-таймер считает вниз с `0xFFFFFFFF`, наблюдение через порт `0x61` (бит 5 = `OUT2`, классический no-interrupt busy-wait для калибровки), разница даёт реальную частоту.

**IOAPIC**: индексный доступ через `IOREGSEL`/`IOWIN`, redirection entry на 2 слова (низкое — вектор/delivery mode, высокое — APIC ID адресата). ISA IRQ1 (клавиатура) роутится на вектор 33, тот же, что раньше обрабатывался через legacy PIC — с точки зрения `interrupt_dispatch()` ничего не изменилось, поменялся только физический источник прерывания.

**Найденный баг (архитектурный, не опечатка):** per-process адресные пространства (`create_address_space()`/`create_user_process()`) наследовали только `kernel_pdpt[0]` (identity map первого 1GB) — жёстко захардкоженный индекс. Как только `paging_map_mmio_2mb()` добавил `kernel_pdpt[3]` для LAPIC/IOAPIC, ни один поток об этом не узнал: первый же `lapic_send_eoi()`, выполненный уже ПОСЛЕ переключения `CR3` на адресное пространство потока A, дал `#PF` (write, not-present) — LAPIC MMIO стал невидим из "приватного" address space. Фикс: `inherit_kernel_pdpt()` копирует **все** заполненные записи `kernel_pdpt`, а не один индекс — будущие MMIO-регионы унаследуются автоматически, без повторного похода в этот код.

### Как устроена UEFI-загрузка (uefi_main.c, build_uefi.sh)

UEFI сильно упрощает жизнь по сравнению с BIOS/GRUB: прошивка **уже в 64-битном long mode** к моменту передачи нам управления — вся ручная эквилибристика из `boot64.s` (page tables, `PAE`/`LME`/`PG`, far jump в 64-битный сегмent) тут просто не нужна.

**Архитектурная проблема, найденная и исправленная до сборки:** `paging64.c` изначально ссылался на `pml4`/`pdpt` как на `extern`-символы из `boot64.s`. Под UEFI `boot64.s` вообще не выполняется — линковка упала бы с undefined reference. Фикс: вынес построение identity map в переносимую C-функцию `paging_init_kernel_map()`, вызываемую первым делом в `kernel_main64()` — теперь ядро не зависит от того, кто именно передал ему управление (GRUB или UEFI), само строит свои page tables и переключает `CR3`.

**Баг, пойманный ПОСЛЕ этого рефакторинга (уже второй раз одна и та же природа):** переставил `paging_init_kernel_map()` on первое место, ещё раньше `fpu_init()` — GCC на `-O2` заинлайнил `alloc_frame()` внутрь и векторизовал обнуление фрейма через SSE (`movaps`), а FPU/SSE ещё не был инициализирован. Мгновенный triple fault (`IDT` пуст, `#GP`→`#DF`→shutdown). Фикс: `fpu_init()` строго первым вызовом в `kernel_main64()`, до абсолютно любого другого кода.

**Сборка** (`build_uefi.sh`): компилирует общие C-файлы ядра с `-fpic -fshort-wchar` (стандартные требования gnu-efi — `-fshort-wchar` обязателен, иначе `L"..."` строки будут неверной ширины для UEFI `CHAR16`), линкует через `crt0-efi-x86_64.o` + `libefi`/`libgnuefi`, конвертирует ELF → PE32+ через `objcopy --target=efi-app-x86_64`.

**Запуск локально:**
```bash
sudo apt install ovmf
mkdir -p esp/EFI/BOOT && cp BOOTX64.EFI esp/EFI/BOOT/
qemu-system-x86_64 \
  -drive if=pflash,format=raw,readonly=on,file=/usr/share/OVMF/OVMF_CODE_4M.fd \
  -drive if=pflash,format=raw,file=/usr/share/OVMF/OVMF_VARS_4M.fd \
  -drive format=raw,file=fat:rw:esp
```

### Как устроен драйвер клавиатуры (keyboard.c)

Классическое разделение на "быструю" и "медленную" часть: `keyboard_handle_irq()` (вызывается из `interrupt_dispatch()` на векторе 33) только читает порт `0x60` и транслирует scancode — никакой тяжёлой логики внутри IRQ-обработчика. Результат кладётся в кольцевой буфер (`kbd_buffer_push/pop`) — по духу так же, как большинство реальных драйверов развязывают IRQ от потребителя данных.

Два отдельных massива перевода — `scancode_ascii` и `scancode_ascii_shift` — переключаются по состоянию `shift_held`, которое обновляется по make/break кодам самих Shift-клавиш (`0x2A`/`0x36` и те же коды с битом `0x80` для отпускания).

### Как устроен heap (heap.c)

Классический паттерн: explicit free-list (двусвязный список блоков по памяти), first-fit поиск, `split_block()` при аллокации (если остаток крупный, режем на два), `coalesce_forward()` при освобождении (сливаем со следующим блоком, если тот тоже свободен; аналогично назад). Каждый занятый блок несёт 4-байтовый magic-номер перед payload — `kfree()` его проверяет, чтобы поймать двойной `free()` или порчу памяти явным паникой вместо тихого разрушения heap.

**Найденный баг (через self-test, не вручную):** `kmalloc(size)` резервировал блок размером ровно `size`, но потом писал 4-байтовый magic *внутри* этого же блока — то есть реальный payload оказывался на 4 байта меньше обещанного. Запись ровно `size` байт (как и должно быть после успешного `kmalloc(size)`) вылезала за границу и затирала заголовок следующего блока. Проявилось наглядно: `heap_print_stats()` показал `free=0xCCCCCCCC` — это буквально тестовый паттern, которым self-test заполнял один из блоков, "просочившийся" в служебное поле соседнего блока. Фикс: резервировать `size + sizeof(magic)`, а не только `size`.

Ограничение: арена фиксированного размера (1 МБ, статический массив) — нет роста по требованию (`sbrk`-подобного механизма). Multi-threading safety теперь есть (`NKern::Lock()`/`Unlock()` вокруг `kmalloc`/`kfree` — см. `nkern_lock.c`), но это защищает только от preemption на ОДНОМ процессоре; настоящая SMP-конкуренция (два ядра одновременно) потребует более тонкой синхронизации, чем простой "big kernel lock".

### Как устроены ring3 + syscalls (gdt64.c, usermode.s, paging64.c)

**GDT/TSS** (`gdt64.c`): полноценная 64-битная GDT строится в C (не в asm — надёжнее для арифметики с адресами): kernel code/data (DPL0), user code/data (DPL3), плюс TSS-дескриптор. TSS нужен ТОЛЬКО для одного: когда прерывание случается, пока CPU в ring3, CPU обязан переключиться на другой стек (`TSS.RSP0`) — без этого ring3-код не может безопасно принять ни один interrupt.

**Переход в ring3** (`usermode.s`): `enter_usermode()` кладёт на стек SS/RSP/RFLAGS/CS/RIP с user-селекторами (RPL=3) и делает `iretq` — единственный штатный способ понизить privilege level.

**Syscall gate** (`idt.c`): `int 0x80` — единственный из 34 векторов с DPL=3 в IDT. Попытка выполнить `int` на любом другом векторе из ring3 даст `#GP` — это и есть защита остальных 33 от прямого вызова из user-space.

**User-mode "программа"** (`paging64.c`): 14 байт машинного кода вручную (нет user-space toolchain в проекте) — `mov eax,1; mov edi,'X'; int 0x80; jmp` в цикле. Своя страница кода и страница стека с USER-битом на **каждом** уровне page table (PML4→PDPT→PD→PT) — упущение хотя бы на одном уровне блокирует доступ аппаратно (AND по всем уровням).

**Найденные баги (методом реальной отладки, не "с первого раза"):**
1. `create_user_process()`'s `PML4[0]` создавался без USER-бита (`0x03` вместо `0x07`) — сам же документировал правило "любой уровень без U-бита блокирует весь путь", но забыл применить его к верхнему уровню. Давало `#PF` при первой же instruction fetch ring3-кода.
2. Перекрытие виртуальных адресов кода и стека (`USER_STACK_VA - 0x1000` случайно совпало с `USER_CODE_VA`) — поймано на этапе написания, до сборки.
3. Спам вывода: ring3-цикл выполняется на порядки быстрее busy-loop потоков A/B — добавлено throttling в обработчике syscall (не в самом ring3-коде, чтобы не трогать тонко откалиброванную раскладку стека).

### Найденный и исправленный баг: непроверенный возврат sched64_create_thread()

При аудите (по чеклисту, адаптированному из практик Symbian user-side разработки — Cleanup Stack/panic-коды переосмыслены под наш bare-metal уровень) обнаружено: `sched64_create_thread()` возвращает `0` при переполнении `MAX_THREADS64` или неверном приоритете, но `main64.c` этот возврат не проверял. Итог — при отказе поток тихо не создавался, а система ушла бы в бесконечный `hlt`-цикл без единого объяснения причины.

Фикс: `neka_panic(category, code)` в `kernel/panic.c` — наш аналог `User::Panic()`. Проверено принудительно (временно урезали `MAX_THREADS64` до 2, чтобы третий `sched64_create_thread()` отказал):

```
*** NEKA PANIC [SCHED] code=0x0000000000000001
System halted.
```

Вместо тихого зависания — явное сообщение с категорией и кодом.

### Три реальных бага, найденных при отладке preemptive scheduler'а

Это тот случай, когда "написал с первого раза и заработало" — редкость в OS-dev, и три найденных здесь бага — хорошая иллюстрация, почему:

1. **SSE без инициализации FPU** — GCC на `-O2` генерирует `movdqa`/`movaps` даже для простых циклов, а `CR0.EM`/`CR4.OSFXSR` после входа в long mode не настроены → `#UD` (invalid opcode) → мгновенный triple fault. Фикс: `fpu_init()` первым делом в `kernel_main64()`.

2. **Нарушение ABI-выравнивания стека** — System V AMD64 требует `RSP % 16 == 8` на входе в функцию (как будто её вызвали через `call`). Наш ручной стек нового потока этого не обеспечивал → как только компилятор использовал выровненную SSE-инструкцию внутри `kprint_hex64`, получали `#GP` (General Protection Fault). Фикс: точный расчёт padding-слота в `sched64_create_thread()`, с явным `__attribute__((aligned(16)))` на стеке потока.

3. **Interrupt gate сбрасывает `IF`, поток теряет прерывания навсегда** — самый тонкий баг. IDT-гейты у нас `0x8E` (interrupt gate), они аппаратно снимают флаг прерываний на входе; обычно он восстанавливается через `iretq` из сохранённого `RFLAGS`. Но поток B впервые стартовал ИЗНУТРИ обработчика IRQ0 (через `ret` в конце `context_switch64`, минуя `iretq`) — значит `IF` остался 0 навсегда, таймер больше не тикал, и B монополизировал CPU (наблюдалось как "тред B крутится бесконечно, A и C голодают"). Фикс: `thread_start64` — trampoline, который делает `sti` перед первым запуском любого нового потока (`context_switch64.s`).

### Файлы preemptive scheduler'а (64 бит)

- `kernel/fpu.c` — `fpu_init()`, включение SSE/FPU state
- `kernel/kernel64.h` — `thread64_t`, `scheduler64_t`, API
- `kernel/sched64.c` — bitmap-scheduler на 64-бит ABI + расчёт alignment padding
- `kernel/context_switch64.s` — свитч контекста (SysV callee-saved регистры) + `thread_start64` trampoline

### Файлы IDT/exceptions

- `kernel/idt.h` / `kernel/idt.c` — структуры дескрипторов, `idt_init()`, `interrupt_dispatch()`, теперь дёргает `sched64_timer_tick()` на IRQ0
- `kernel/isr.s` — 32 CPU-exception stub'а + IRQ0/IRQ1, сохранение полного регистрового состояния
- `kernel/terminal64.c` — вынесенный `kprint`/`kprint_hex64`/VGA+serial init
- `kernel/timer64.c` — `pic_remap()`/`pit_init()`
